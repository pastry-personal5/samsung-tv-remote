# P2-M6 control contract draft

Status: M7 application contract and M8 fake-profile `/v1` implemented; production
cutover and MCP remain M9–M10. This is not a
claim that `/v1` or `/mcp` exists in the shipped app. A signed lifecycle and
Keychain prototype and a real Claude Code connection to the product server
remain release gates.

The [2026-11-11 acceptance record](milestone-06-acceptance.md) fixes owner
choices and assigns production verification to M7–M11. MCP confirmation is
an explicit typed step; human approval belongs to the client, with TV-side
Pairing approval still required.

The [M8 wire decisions](milestone-08-wire.md) freeze canonical scoped IDs,
mandatory epoch context, decimal-string counters and strict fields. The isolated
first profile is empty and imports no legacy data or credentials.

## Common envelope and admission

`ClientIdentity` is assigned by authentication. It is never a JSON field. A
fresh random `server_epoch` identifies each process lifetime. Within an epoch,
`selection_generation` starts at zero and increases whenever selection is
explicitly changed, including reselecting the current saved TV. The runtime
fences the current session even for the same ID; a separate Connect request
establishes remote readiness. A GUI may sequence that explicit follow-up as
part of its select-TV interaction. Restoring a selected ID on server
startup does not reconnect and does not pretend to restore the old generation.
Each saved device also has an epoch-scoped `config_revision`, initialized to
zero from the restored repository and incremented only after a durable Wake
configuration or re-pair metadata change. The current `devices.json` v2 has
no revision field. Epoch plus config revision guards concurrent edits; a
restart changes epoch and requires a fresh snapshot, so no v2 file-format
migration is needed solely for this counter. Forget fences the target while
its store removals are pending.

Every mutation has `server_epoch` and `operation_key` (a UUID generated by the
client once per user intent). Select also has `expected_generation`; selected
TV control has `device_id` and `selection_generation`; setup uses an expiring
`attempt_id` and, where appropriate, `observation_id`. Configuration and
forget use an explicit saved `device_id` and a revision precondition so that
another client's edit cannot be silently overwritten. A first Pairing may
commit and select its new device only if the generation observed when the
attempt began still matches. A changed generation invalidates the attempt
before storage commit; its in-memory TV-issued token is discarded and the
result reports stale rather than silently selecting or saving. Re-pair
requires the current saved ID and generation.

Discovery candidates bind a host to the creating client, epoch and discovery
attempt; probe validates the host again before network use. A probe creates
one attempt/observation pair bound to its creator, canonical host, full
certificate fingerprint, epoch and selection generation at probe start.
Changing the address, selection or epoch invalidates that observation.
Pairing must present both IDs and the exact fingerprint before expiry; the
owner checks those bindings again immediately before the durable commit.
Another authenticated client may inspect shared selected-TV state but cannot
consume or confirm this client's observation. Re-pair also binds the saved ID
and its current host, preventing a late result from updating a different TV.

The owner indexes `(authenticated client identity, operation_key)`. It checks
this index before mutable preconditions. Reuse with the same normalized typed
payload returns the original receipt/result; reuse with a different payload
returns `operation_key_conflict`. All admitted results, including typed policy
rejections, live for 30 minutes after terminalization. Pending operations do not
expire. The owner admits no new operation when the 32,768-record registry is
full; it does not evict a retained result early. The terminal result records
its expiry; a pending receipt does not guess one. Restart loses this in-memory
index; an old-epoch lookup reports
`unknown_after_restart`, never `not_sent`. After eviction, a same-epoch
lookup reports `outcome_unavailable`: the server cannot distinguish an
expired operation from a key that was never admitted without retaining an
unbounded tombstone. A repeated key after eviction may be admitted as new,
so a client must not automatically submit it. The client obtains a new
snapshot and requires an explicit new user intent before repeating a TV side
effect. There is no exactly-once guarantee across a restart or after expiry.

The 30-minute/32,768-record pair allows roughly 18 new operations per second
for a sustained half hour before capacity pressure, while bounding memory.
The [M7 completion review](milestone-07-review.md) records measured memory,
resource limits and timings. At capacity the owner refuses new admission
without shortening deduplication retention. The global 32,768-record bound
also has per-client quotas of 8,192 retained and 64 pending operations.

The external owner mailbox has 128 requests. Completion/lifecycle delivery is
independent: at most eight joined effect results, a dedicated drain signal
and a 32-event session lane. This replaces the proposed generic 32-completion
mailbox. Remote capacity is 32 waiting plus one writer. At most eight
non-remote effects run, including timed-out blocking workers. Discovery/probe
starts conservatively require fewer than two existing workers. One serialized
storage lane spans all IDs. Drain/completions/timers have priority and ingress
has an opportunity at least every 16 owner transitions. The HTTP mutation body limit is 16 KiB; M8 also enforces the runtime's
type-specific field limits. Maximum-envelope fixtures are in
`tests/control_wire.rs`.

M7 fixes candidate caps at 1,024 global/64 per client and 32 per discovery;
observations at 128 global/eight per client; subscribers at 64 global/four per
client with 64 events each. Keys are 128 bytes, hosts 253, Pair labels 80
(input-envelope maximum 256), probe name/model fields 256 each, saved labels
256, and saved records 1,024. Oversize profiles block instead of truncating.
Both candidate and observation authority is client/epoch bound. Detailed
outcomes remain private to their owning client; coarse phase/ID events are
visible to all authorized observers.

Candidate and observation handles expire 2 and 5 minutes after publication,
respectively, and are invalid after an epoch change. Discovery has a 10-second
deadline, probe 20 seconds, TV Pairing approval 90 seconds, ordinary connect
75 seconds, remote socket write 4 seconds, and Wake reconnect 30 seconds.
These are outer supervision ceilings, not replacements for
existing stage timeouts or permission to extend user-visible waits. Preserve
the current 5-second SSDP search, 8-second connection stages, 45-second TV
approval wait, 4-second write, 2-second disconnected-power probe, and 30-second
Wake window during extraction. The M7 review records the stage-by-stage table and fake-time evidence.
Pair preparation is capped at 80 seconds plus a 10-second commit report;
Connect, disconnected Power and Wake readiness include their storage stages.
Storage and packet-send reporting deadlines are 10 seconds; storage keeps
its worker/fence and a packet deadline revokes its permit without dropping
the worker. Total remote lifetime, including FIFO residence, is 136 seconds. Any user-visible timeout change requires
a documented rationale and acceptance. These deadlines are not automatic
retries. A deadline after
possible TV or packet transmission yields `uncertain` for that effect; a
deadline before transmission yields `not_sent`. Workers must return a tagged
completion or be supervised into such a terminal result. M7 preserves the existing 5-second SSDP, 8-second connection, 45-second TV
authorization, 4-second write, and 30-second Wake reconnect stages.

The M7 in-process runtime reports drain within 5 seconds after closing
mutation admission, or immediately once workers settle. Read-only queries
remain available during settlement. Its drain handle reports outstanding
effects and unresolved storage; an interrupted storage operation is uncertain,
never reported as rolled back. Blocking workers retain their slot/fence after
the report, and the composition layer must await handle settlement before
opening the same profile with another owner. This is a reporting deadline,
not a process-exit deadline. Durable recovery is covered by the M7 review; process-exit and sticky-stop
policy still need the later lifecycle evidence.

### Result vocabulary

| Kind | Terminal facts a client may say |
| --- | --- |
| Remote action | `not_sent` with reason, `written` to the Samsung socket, or `uncertain` after a possible write. `written` never means the physical state changed. |
| Wake | `packet_not_sent`, `packet_sent`, or `packet_uncertain`, plus a separate `remote_not_ready`, `remote_ready`, or `readiness_unknown` observation. A reconnect cancellation cannot erase `packet_sent`. |
| Connect | `remote_ready`, `offline`, `pairing_required`, `certificate_changed`, `blocked`, or `uncertain`; no physical power claim. |
| Discovery and probe | Bounded candidates or one certificate observation, each with an expiry, or a typed failure. No pairing is implied. |
| Pair or re-pair | `tv_approved_and_saved`, `tv_denied`, `observation_expired`, `stale_selection`, `blocked_partial_setup`, or a typed transport/storage failure. Stale completion cannot commit a new record. |
| Select, configuration, forget | Durable selection/configuration revision or per-store forget completion; partial cleanup is `blocked_partial_setup`, not success. |

Accepted/queued/running are progress states. They are never physical outcomes.
Disconnecting an HTTP request does not cancel its operation. `cancel_wake`
applies only to the named Wake operation: before send it may be `packet_not_sent`;
after send it only stops reconnect attempts. Selection or Stop terminalizes
waiting remote work as `not_sent`, while an interrupted in-flight write is
`uncertain` unless the transport reports a definitive result. Discovery/probe
may be cancelled before their observations are published. Pairing cannot be
cancelled as if TV approval or a storage commit were undone.

### Operation matrix

| Intent | Guard before effect | Effect and terminal fact | Cancellation boundary |
| --- | --- | --- | --- |
| Discover | Current epoch, capacity | SSDP search; bounded expiring candidate IDs | Before result publication only. |
| Probe | Current epoch, local host or live candidate | Secure endpoint probe; full observed fingerprint bound to attempt | Before observation publication only. |
| Pair / re-pair | Live observation, exact fingerprint confirmation, generation; re-pair ID/host match | TV approval, then serialized token/trust/device commit; typed Pairing result | Before approval may stop waiting; after approval/commit report factual outcome or partial block. |
| Select | Expected generation, saved ID | Durable selected-ID write, then new generation/event | Before durable write; after write selection is committed. |
| Connect | Selected ID/generation and valid trust/token | Secure session and remote-readiness observation | A cancelled or late session is closed; no state adoption. |
| Set Wake | Selected saved ID/generation, config revision, valid MAC/active choice | Durable config revision | Before durable write only. |
| Remote action | Selected ID/generation, Pairing and connection, FIFO room | One dispatched key; `not_sent`, `written`, `uncertain` | Waiting can be unsent; in-flight may be uncertain. |
| Disconnected Power Toggle | Selected ID/generation, Wake configuration, Pairing material | Probe, then one Wake packet only for offline/timeout; separate readiness result | Before packet can be unsent; after packet preserve sent fact. |
| Wake | Selected ID/generation, valid local-route Wake config | One UDP packet, then reconnect observation | Same packet boundary; cancel only reconnect after send. |
| Forget | Saved ID/config revision, exact ID confirmation | Fenced Keychain/trust/repository removal; per-store fact | Once first removal starts, complete or retain recovery marker. |
| Stop server | GUI management capability, current epoch | Durable sticky-stop marker, then admission drain and listener close | After marker is durable, only explicit GUI Resume may clear it. |
| Operation lookup / subscribe | Authenticated identity | No TV effect; same owner registry/snapshot | Cancelling query/stream does not cancel operation. |

Wake captures validated configuration at admission; later configuration edits
apply to new operations. Selection, forget and Stop fences still apply before
the single send. M7 tests edits racing packet transmission. The temporary GUI maps guarded
recovery to exact-target service commands: partial Forget retries incomplete
steps with its transaction; interrupted first Pairing compensates its reserved
ID; interrupted re-pair/rotation requires a fresh probe and TV approval bound
to its recovery transaction. The M8 wire adapters must preserve these guards.

Starting the server and listing MCP tools have no TV-network effect. The GUI's
current launch reconnect becomes a separate `Connect` request after attach;
an MCP-only connection never discovers, pairs, connects or Wakes a TV.

## `/v1` JSON and event surface

All routes require authentication, including reads, readiness, and events.
Mutation HTTP response `202` is an operation receipt, not success at a TV.
The owner may return an already terminal operation with `200`. URL IDs are
opaque UUIDs; no host or credential appears in a URL. Request/response DTOs
are versioned at the adapter and map explicitly to application types.

| Route | Input / result |
| --- | --- |
| `GET /v1/ready` | Authenticated serving/build/API/epoch check; says nothing about TV or Keychain readiness. |
| `GET /v1/state` | Atomic snapshot: epoch, revision, selected ID, generation, saved-device summaries and per-device config revisions, Pairing/connection/Wake facts, recent operation references. |
| `GET /v1/devices/{id}` | Safe saved metadata and Wake settings; no token or raw certificate. |
| `POST /v1/discoveries` | Common mutation envelope; receipt for bounded SSDP discovery and candidate handles. |
| `POST /v1/probes` | Envelope plus validated local `host` and optional client-bound `candidate_id`; receipt for a certificate observation. |
| `POST /v1/pairings` | Envelope, attempt and observation IDs, exact full observed fingerprint, explicit confirmation, label, required observed generation, optional re-pair device ID. TV approval and durable commit are later results. |
| `POST /v1/selection` | Envelope, `device_id`, `expected_generation`; receipt followed by durable selection event and new generation. |
| `POST /v1/connections` | Envelope, selected `device_id` and generation; optional boolean `only_if_idle` defaults false. When true, owner admission requires a disconnected idle selection and rejects ready/Connect/Pairing/Wake/storage/recovery conflicts without disturbing them. Receipt for remote readiness. |
| `PUT /v1/devices/{id}/wake` | Envelope, saved ID, `selection_generation`, `expected_config_revision`, validated wired/Wi-Fi MACs and active interface; receipt for durable update. |
| `PUT /v1/devices/{id}/sources` (P3-M2) | Envelope, selected ID, generation, `expected_config_revision` (shared with Wake) and a full four-key `sources` replacement; receipt for durable update. `remote-actions` also accepts `Hdmi1`–`Hdmi3`, `Tuner` and `SourceMenu`; an unconfigured or hidden port is rejected `source_unconfigured`/`source_hidden` (412). |
| `POST /v1/remote-actions` | Envelope, selected ID, generation, semantic `RemoteAction` enum; receipt for one tracked action. `PowerToggle` owns disconnected probe-then-Wake; `PlayPause` is resolved by the server at dispatch. |
| `POST /v1/wakes` | Envelope, selected ID and generation; receipt for one packet attempt and subsequent readiness observation. |
| `POST /v1/wakes/{operation_id}/cancel` | Envelope, selected `device_id` and `selection_generation`; receipt for cancellation request, not a packet recall. |
| `POST /v1/devices/{id}/forget` | Envelope, ID, `expected_config_revision`, `confirm_device_id` equal to ID; receipt for serialized removal with per-store result. |
| `GET /v1/operations/{id}?epoch=...` | Owner-authorized operation progress/result. Other clients see the shared state event but cannot read a different client's private operation details. |
| `GET /v1/operations/by-key/{key}?epoch=...` | Lost-response lookup scoped to authenticated client. Old epoch is `unknown_after_restart`. |
| `GET /v1/events` | SSE: one atomic `snapshot`, then ordered `state_changed`/`operation_changed` revisions, or `resync_required`. |
| `POST /v1/server/stop` | GUI management capability, epoch and operation key; persist sticky Stop before acknowledging, drain/terminalize effects, then close listeners. A lost response is checked from the owner-only marker and authenticated readiness, without restarting. |
| `POST /v1/devices/{id}/recover-pairing` | Envelope, matching `device_id`, exact `transaction_id` and `confirm_device_id`; compensates an interrupted first Pairing only. Re-pair recovery requires fresh Pairing approval with `recovery_transaction_id`. |
| `POST /v1/devices/{id}/recover-forget` | Envelope, matching `device_id`, exact `transaction_id` and `confirm_device_id`; retries the marker's remaining removals even when the device record is gone. |

Resume is an explicit signed-GUI launcher action. While no server is
listening, the launcher acquires the per-user lifecycle lock, validates the
owner-only marker, atomically clears it, and starts or attaches to a server.
An MCP header helper must return a stopped error and cannot clear the marker.
No MCP tool controls server lifecycle. Stop and Resume are process management,
not TV control, and neither replays a TV action.

[Synthetic requests and outcomes for every existing operation](milestone-06-api-examples.md)
fix the intended meaning of these routes for implementation review.

Example request and receipt (synthetic IDs):

```json
{"server_epoch":"e1111111-1111-4111-8111-111111111111","operation_key":"a2222222-2222-4222-8222-222222222222","device_id":"d3333333-3333-4333-8333-333333333333","selection_generation":"7","action":"VolumeUp"}
```

```json
{"operation_id":"53545201-0100-0000-0000-000000000001","server_epoch":"e1111111-1111-4111-8111-111111111111","device_id":"d3333333-3333-4333-8333-333333333333","selection_generation":"7","state":"pending","result":null}
```

`operation_id` and epoch use canonical UUID spelling. All timestamps are UTC.
The [M8 wire decisions](milestone-08-wire.md) define scoped ID layout,
lossless decimal-string counters, exact DTO fields, and parsing policy. `expires_at_unix_ms` is
absent while pending and set when the terminal result is
recorded. On a stale request, `409` includes the current epoch, selected ID,
and generation after authorization, so the client can refresh without a blind
retry. Responses never include a Pairing token.

| HTTP status | Stable error code | Meaning / next step |
| --- | --- | --- |
| `400` | `invalid_request`, `invalid_target`, `invalid_confirmation` | Fix input; no operation admitted. |
| `401`, `403` | `unauthenticated`, `forbidden` | Reauthenticate or reconnect; no effect admitted. |
| `404` | `not_found` | Unknown saved target. Operation lookup without a retained result uses `410`. |
| `409` | `stale_epoch`, `stale_selection`, `stale_config`, `operation_key_conflict`, `observation_expired` | Read state or re-probe; no new effect admitted. |
| `410` | `outcome_unavailable`, `unknown_after_restart` | Key lookup has no retained result or the epoch changed; outcome cannot be recovered, so never auto-replay. |
| `412` | `pairing_required`, `certificate_changed`, `confirmation_required` | Complete a fresh guarded setup step. |
| `423` | `storage_blocked`, `partial_setup` | Resolve locked/denied/interaction-required Keychain or recovery marker. |
| `429` | `busy` | Capacity full; lookup same key if admission was ambiguous. |
| `503` | `transport_unavailable`, `storage_unavailable`, `server_stopping` | Service unavailable; inspect operation before repeating. |

Malformed or unauthenticated input, a stale epoch, key conflict, or ingress/
registry-capacity rejection is not admitted and has no new operation record.
For a current-epoch new key with registry space, the owner reserves its record
before evaluating mutable policy; a stale selection/configuration, expired
observation, missing Pairing or target, and similar policy rejection is a
retained terminal result. Its response uses the table’s HTTP status and error
code and includes `operation_id`, `server_epoch`, and `expires_at_unix_ms`. The HTTP
status alone does not determine admission. A known duplicate returns the
original record even when the registry is full. A rejected FIFO/effect-capacity
check is retained as terminal `busy` when a registry slot was reserved;
ingress or registry saturation cannot promise retention. No rejected request
starts a TV effect. Error bodies use
`{ "error": { "code": "..." } }` and optionally a safe `current` precondition object and the admission metadata
above; no internal stack or host.

`GET /v1/events` registers its subscriber and captures the initial snapshot
in one owner transition. The snapshot has revision `r`; later messages must
have consecutive revisions `r+1`, `r+2`, and so on. There is no independent
read-then-subscribe gap. Each subscriber has a 64-event buffer. On overflow,
the server sends `resync_required` if it can, then closes the stream; the
client discards its projected copy and gets a new atomic subscription. No
retained replay is promised. Event revision is per epoch. Operation results
remain in the registry independent of event delivery or acknowledgments.
Every global revision is emitted to every authorized subscriber. For an
operation belonging to another client, `operation_changed` contains only its
opaque ID and coarse phase, with no request payload, host, certificate,
confirmation or terminal detail. The owning client can use its authenticated
operation lookup for the full safe result. This preserves consecutive global
revisions without leaking another client's operation input. A subscriber may
ignore a coarse event, but must still advance its revision cursor.

## Two-client sequence to test

1. GUI and MCP read selected TV A, epoch E, generation 7.
2. GUI submits remote key K for A at E/7; the owner admits it. Its socket
   write starts and the TV-side effect becomes unknowable after a disconnect.
3. MCP submits selection B with `expected_generation: 7`. After the durable
   write, the owner publishes B/8. K completes `uncertain`; it is never sent
   to B and never replayed.
4. GUI submits another A key at E/7 and receives `stale_selection` with B/8.
5. GUI attempts to select A with expected generation 7 and is rejected. Only
   a new user intent based on B/8 may select A.
6. If K's HTTP response was lost, GUI looks up its original key. If the
   process crashed, E changes; lookup reports `unknown_after_restart`.

## MCP revision and target-client evidence

Implement `2026-07-28` Streamable HTTP first, with one authenticated POST
`/mcp` endpoint, mandatory `server/discover`, and no legacy GET stream or
protocol sessions. The initial supported set is `["2026-07-28"]`;
unsupported versions return that list. A legacy revision, if later required,
must be implemented according to its own specification. An isolated Claude
Code 2.1.300 health check sent `server/discover` followed by `tools/list`,
each with matching `2026-07-28` header and `_meta`, and ran a fake
`headersHelper`. When modern discovery failed, it fell back to
`initialize`/`2025-11-25`. This proves CLI revision support against a minimal
fake endpoint, not operation or signed-server compatibility. The local
credential mode intentionally does not advertise an OAuth authorization
server: a user explicitly connects Claude Code and a signed bundled helper
supplies a separate revocable MCP bearer header. Every call is authenticated
before the application owner. Tool-list caching is private to that identity,
with a five-minute TTL and invalidation on upgrade/credential change; TV
state does not change the catalog.

The `server/discover` result advertises the supported revision, tools
capability, private cache hint and brief shared instruction. On modern
requests, the server validates `MCP-Protocol-Version`, `Mcp-Method`, required
`Mcp-Name`, and matching per-request `_meta`; a mismatch is rejected before
service admission. Authentication and Origin checks precede protocol
handling. The HTTP GET and handshake rules of the 2025 era are not implemented
in the selected first revision.

The semantic catalog is: `list_tvs`, `inspect_tv`, `discover_tvs`, `probe_tv`,
`pair_tv`, `select_tv`, `connect_tv`, `set_wake`, `remote_action`, `wake_tv`,
`cancel_wake`, `get_operation`, `forget_tv`. These map one-to-one to the above
service operations where possible. `remote_action` takes the finite action enum,
never a Samsung key string. `pair_tv` and `forget_tv` require the same exact
target and confirmation fields as `/v1`. Every mutation takes epoch and a
client operation key; selected-TV effects also take generation. `get_operation`
may wait at most 10 seconds without altering the effect. Read results are
bounded summaries; Pairing observation results retain the full fingerprint.
Discovery and probe tools may wait within their supervised deadlines for a
terminal observation; if still running, they return a receipt and the client
uses `get_operation`. The five-call setup corpus assumes both finish inside
that bounded wait and Pairing needs one later lookup. A slow effect can add
calls, which M10 must count rather than hide in a token-only estimate.
Errors and receipts retain target, epoch, generation, code, and safe next
step. `structuredContent` plus a terse text fallback is the conservative
initial representation; M10 must count both model-visible copies before
claiming a token saving.
